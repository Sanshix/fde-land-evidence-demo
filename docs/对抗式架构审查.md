# 对抗式架构审查（第一性原理视角）

> 审查对象：当前 `demo` 工程（Python 3.12 + FastAPI + SQLite + 原生 JS，单 worker、单后台识别线程）。
> 视角：回到"项目要解决的根本问题 + 不可动摇的约束"，逐层拷问设计，而非对照业界惯例。

## 一、核心目标与不可动摇的约束

**根本问题**：把约 3000 份国有土地租赁合同（扫描件 / PDF / DOCX / XLSX，整包 ZIP）从"原件"变成"可核算、可追溯、可催缴的一宗一档台账"。

**不可动摇的事实约束（来自赛题与 README，且被代码固化）**：
1. 人工智能只做识别、抽取、比对、提示；**金额只由规则程序 `domain.compute` 计算**；所有模型结果"待确认"，人确认后才入库（赛题五(3)）。
2. **数据不出网是硬约束**：公网模型仅接收"已授权哈希"或 `competition_simulated` 模拟材料；内网/本机模型可放开。
3. 运行环境：单文件 SQLite（单 writer）、单进程、单后台识别线程、原生前端无 CDN。
4. 审计与原件证据不可篡改、不可删（触发器 + SHA256 清单）。

**经第一性原理确认"真正必要"的抽象**：
- 规则引擎与模型彻底解耦（`domain.py` 不读 OCR/网络）✓
- 人工确认门禁 + 乐观并发 `draft_hash`/`version` ✓
- 审计/出版物不可变 + 原件留存 ✓
- 外发 SHA 白名单 + 内网放行 ✓

**经第一性原理判定"未经论证的假设 / 过度 / 盲从框架"**：
- 假设"确认一份材料必须扫描全库已发布材料来校验票据归属"——无第一性理由。
- 假设 SQLite 单实例 + 写事务内全表扫描能扛 3000 份并发确认。
- 假设"凭据/角色由请求头声明即可"（demo 模式）——直接违反"认证/授权不得依赖客户端输入"。
- 级联多模型（primary/secondary/third/context + document_cascade + 4 种 OCR 协议）复杂度极高，但其前提"多独立模型能提升可入库准确率"在 README 自承"没有一份关键字段全对（承租人 22%、坐落 0%）"下收益存疑。
- "金额只由规则算"在取整口径未获主管部门书面确认前并不成立（默认 `half_up` 与标准答案二进制 round 在 5 宗地差 1 分）。

## 二、问题清单（按严重程度分级）

### 🔴 严重（P0）

**P0-1　确认 / 预览 / 费率变更在写事务内全表扫描 × 全量缴费表重建 → O(N²) 锁竞争**
- 位置：`app/main.py:574-590`（`validate_payment_ownership` 遍历 `SELECT … WHERE state='published'` 全表）、`app/main.py:519-561`（`confirm` 在 `BEGIN IMMEDIATE` 内调用）、`app/main.py:667-712`（`batch_confirm`）、`app/main.py:961-1033`（`rate_impact` / `confirm_rules`）、`app/business.py:565-571`（`selected_receipts` 对**每一行**重建 `{序号:行}` 全量缴费字典）。
- 违反第一性原理：校验"一张票据只归入一宗"本质应"按宗地/票据建索引反查"，却在每次确认把全部已发布文书逐行扫一遍、并对每行把整张缴费表（`source["payments"]`，启动时一次性读入、数千行）重新 `dict` 化。这是 O(已发布文书 × 缴费行数) 的纯浪费，且全部跑在 SQLite 唯一写锁内。
- Stakeholder 一行影响：3000 份规模下，单人批量确认或一次费率变更会长时间独占写锁，冻结所有经办人员的导入 / 确认 / 查询，整系统"卡死"。
- 最小改进：① 在 `init()` 补索引 `documents(state)`、`documents(parcel_id,state)`、`publications(parcel_id)`；② 把 `source["payments"]` 在启动时建成 `序号→行` 一次复用，不要在循环里重建；③ 维护一张"宗地→已选票据号"索引（随 publication 写入/更新），校验改为集合差集，而非逐行扫全库。

**P0-2　`recognizing`/`running` 死锁无管理端逃生口**
- 位置：`app/store.py:95-98`（仅在**启动时**把 `running→interrupted`、`recognizing→needs_human`）；`app/main.py:372-394`（`retry` 在 `queued`/`running` 时返回 409）；无"强制重置识别任务"端点。
- 违反第一性原理：后台识别线程若在本机 OCR（numpy / rapidocr 的 C 扩展）中**崩溃/段错而非抛异常**，任务永久停在 `running`、文档永久 `recognizing`；只有重启进程才能恢复（重启影响全体用户），而 `retry` 永远 409。
- Stakeholder 一行影响：一份材料卡死即无法重试 / 重导，只能重启服务，打断所有在线用户。
- 最小改进：① worker 加 watchdog（任务超时未在 `run_cloud_cascade` 内完成则标记 `failed`）；② 提供管理员"强制重置识别任务"端点；③ 或把 `running` 视为可重试（带 attempt 计数，超限转人工）。

**P0-3　Demo/loopback 模式无授权，角色与经办人由请求头任意声明**
- 位置：`app/main.py:46-57`（`actor()` 在 `auth.users()` 为 None 时 `role = request.headers.get("x-fde-role")`）；`app/main.py:247-257`（仅当 `FDE_USERS_FILE` 存在才校验）；`scripts/start.sh:11-20`（仅在监听非回环时强约束账号）。
- 违反第一性原理：**授权决策绝不可依赖客户端输入**。当前 demo 模式把"本机演示身份"当作生产认证边界。
- Stakeholder 一行影响：任何本地进程/脚本带 `x-fde-role: admin` 即可获得管理员并伪造经办人姓名写入审计；一旦有人绕过 `start.sh` 直接 `uvicorn --host 0.0.0.0` 且漏配 `FDE_USERS_FILE`，公网任意用户即管理员。
- 最小改进：删除"无账号时由请求头取角色"分支；demo 模式只给 `viewer`/`reviewer` 且响应明确标记 `non-production`；admin 操作必须存在**已验证**身份；或在代码内硬性断言"非回环监听 ⇔ 已启用账号"，而非只靠 `start.sh` 预检。

### 🟠 高（P1）

**P1-1　上传 / 批量导入把整包读入内存，无流式、无磁盘暂存**
- 位置：`app/main.py:344`（`await f.read(25*1024*1024+1)`）、`app/main.py:1202`（`await file.read(150*1024*1024+1)`）；`intake.ingest` 再落盘。
- 违反第一性原理：大文件应先落临时文件再解析，而非常驻进程内存。
- Stakeholder 一行影响：40×25MB 或 150MB ZIP 直接占 1GB+ 内存，一次请求即可把服务打 OOM；无鉴权的 demo 模式更可被反复灌爆。
- 最小改进：`UploadFile` 流式写入临时文件后交给 `ingest`；加请求体上限与并发导入数限制。

**P1-2　`notice()` 在关键源文档被重新处理（`review=NULL`）后取 `latest_doc["review"]["fields"]` 直接 500**
- 位置：`app/main.py:816-832`（`latest_doc = store.doc_row(...)` 后 `latest_doc["review"]["fields"]`）。
- 违反第一性原理：对历史快照的引用应防御空值。已发布宗地的 `latest_document` 指向的文档若后来被补件/调页（`attach_payloads` 会把 `review` 置 NULL、`state` 改 `queued`），`store.doc_row` 仍返回该文档但 `review` 为 None。
- Stakeholder 一行影响：已发布宗地只要其关键源文档后来被补件，点"生成催缴通知"即报错，阻断催缴流程。
- 最小改进：`review` 为 None 时回退到 publication payload 内已固化的字段，或拒绝并提示"源文档已变动，请重新确认后再生成"。

**P1-3　费率变更确认在单写事务内对每一宗地重算并 publish**
- 位置：`app/main.py:1006-1018`（`confirm_rules` 内 `rate_impact` 持有写锁循环全部宗地）、`app/main.py:961-980`（`rate_impact` 内嵌 `calculate_documents` + `validate_payment_ownership` 全扫描）。
- 违反第一性原理：变更影响预览可异步/分批，确认不应在持锁时长循环 3000 宗地、每宗再触发 P0-1 的全扫描。
- Stakeholder 一行影响：一次合法的费率调整（admin 偶发操作）会让服务在写锁内冻结分钟级，全体用户不可用。
- 最小改进：费率变更改为后台任务 + 进度；或逐宗提交（每宗一事务），不一次性持有全局写锁。

### 🟡 中（P2）

**P2-1　热路径缺索引（`documents(state)`、`documents(parcel_id,state)`、`publications(parcel_id)` 全表扫描）**
- 位置：`app/store.py:44-81`（`init()` 无 `CREATE INDEX`）；`app/main.py:584`、`app/main.py:1413-1422`、`app/operations.py:26-32`。
- 违反第一性原理：这些过滤/排序是每请求热路径，应索引；`publications` 随确认历史只增不减，按 `parcel_id` 查最新快照全扫会随规模恶化。
- Stakeholder 一行影响：台账 / 统计 / 提醒 / 导出每次按宗地查最新快照都全扫 publications，历史越积越慢。
- 最小改进：在 `init()` 加 `CREATE INDEX IF NOT EXISTS` 于上述列（与 P0-1 同源，一并修）。

**P2-2　`/api/status`、`/api/governance`、`/api/export` 全量加载所有文书大 JSON**
- 位置：`app/store.py:122-124`（`list_docs` 为 `SELECT *` 全量解析）；`app/main.py:287-299`、`1329-1352`、`887-921`。
- 违反第一性原理：状态轮询与治理队列不必每次拉取全部文书（含 `pages`/`result` 识别证据大 JSON）。
- Stakeholder 一行影响：前端轮询 `status` 会把全部文书反复序列化进内存，3000 份下每次数十~数百 MB，拖慢并可能 OOM。
- 最小改进：状态接口只返回计数 + 最近 N 条；治理/导出走服务端分页或流式。

**P2-3　单识别线程串行，无并发、无水平扩展**
- 位置：`app/main.py:162-241`（进程内 daemon 线程）；`scripts/start.sh:21`（`--workers 1`）。
- 违反第一性原理：识别是 CPU/网络密集且慢（云端约 40s/份），单线程串行是吞吐天花板，且线程崩溃即丢失队列驱动。
- Stakeholder 一行影响：3000 份按 40s/份需约 33 小时，达不到"3,000 份时效测算"；且进程内线程挂掉即停摆。
- 最小改进：识别任务外置为独立 worker 进程/队列（文件队列或 RQ），与 API 解耦、可多实例；至少允许多识别线程 + 任务表悲观锁。

**P2-4　数据外发范围仅靠配置布尔值，无运行时"非回环 + 公网模型 + 非授权范围"拒绝断言**
- 位置：`app/providers.py:140-157`（`approved_input` 按 `authorized_scope` 放行）；`scripts/start.sh` 不校验 providers 配置。
- 违反第一性原理：政务数据出网须满足"已授权范围"，但范围判定是配置文件值；部署误用（prod 指向 `providers.competition.json`）即把真实合同外发到公网模型。
- Stakeholder 一行影响：配置失误即触发真实合同泄露到公网，且过程无报错。
- 最小改进：启动时断言"监听非回环 ⇔ 禁用 `competition_simulated`/任意公网外发"，否则拒绝启动；把 `authorized_scope` 与部署环境强绑定校验。

**P2-5　取整口径未定，系统产出的金额即"待确认口径"**
- 位置：`app/domain.py:66-93`（`rounding_mode` 默认 `half_up`）；README 自承 5 宗地差 1 分。
- 违反第一性原理："金额只由规则程序计算"隐含"规则须被主管部门确认"；在未确认前产出的金额可能与法定口径差 1 分（累计可能更大）。
- Stakeholder 一行影响：台账 / 催缴 / 税务推送的金额在正式口径书面确认前存在合规风险。
- 最小改进：取整方式设为显式配置项、默认告警"未确认"，并在导出/催缴页标注口径状态；推动主管部门书面确认。

### ⚪ 低（P3）

**P3-1　`documents` 表可改，而 `publications`/`audit` 不可改**
- 位置：`app/store.py:63-97`（仅对部分表加 UPDATE/DELETE 触发器）。
- 违反第一性原理：已发布文书的 canonical 记录应不可变。
- Stakeholder 一行影响：published 文档的 `review` 在库内可被 SQL 改（虽无接口直接改，但 admin/漏洞可篡改且审计只记不挡）。
- 最小改进：对 `documents` 关键列加 UPDATE 触发器，或已发布 `review` 只存 `publications`。

**P3-2　`compute` 对"无有效合同但有缴费"返回负欠缴**
- 位置：`app/domain.py:486-493`（`arrears = total_due - total_paid`，未取 max(0,·)）。
- 违反第一性原理：欠缴语义应为非负。
- Stakeholder 一行影响：台账显示负欠缴，易误导经办人。
- 最小改进：`arrears = max(0, total_due - total_paid)`，并在 ledger 标注"多缴"。

**P3-3　级联识别复杂度收益未经实证**
- 位置：`app/cloud_cascade.py`（`run_cloud_cascade` / `run_document_cascade`）、`app/providers.py`（`identify_qianfan` / `identify_baidu_ocr` / `identify_local` 四种协议）。
- 违反第一性原理：在 README 自承 OCR 准确率极低（承租人 22%、坐落 0%）下，级联主要增加延迟/成本/维护面，未必提升可入库准确率（仍"全部送人工复核"）。
- Stakeholder 一行影响：每页多模型调用推高费用与等待，却未量化换来多少可入库率提升。
- 最小改进：用练习集实测量化"级联 vs 单模型"在可入库率上的增益；无显著增益则降级为单路径 + 人工复核，削减 4 协议维护面。

**P3-4　worker 任务领取非原子（SELECT queued 后另开连接 UPDATE running）**
- 位置：`app/main.py:164-183`。
- 违反第一性原理：若误开 `--workers>1`，两个 worker 会重复领取同一任务。
- Stakeholder 一行影响：多 worker 部署下同一文书被重复识别、结果互相覆盖。
- 最小改进：用单条 `UPDATE … WHERE state='queued' RETURNING id` 原子领取，或显式 `BEGIN IMMEDIATE` 包裹领取。

## 三、总体判断：架构中最脆弱的一处

**最脆弱点 = P0-1：核心写路径（确认 / 批量确认 / 费率变更）在 SQLite 唯一写锁内做"全表扫描 × 全量缴费表重建"的 O(N²) 校验。**

理由（为什么它是根而不是表象）：
- 它直接命中"人工确认入库"这一**唯一核心闭环**——项目存在的意义就是把材料确认进台账；而这条路径在规模上会自我坍缩。
- 它随数据量**平方级恶化**：确认第 N 份材料成本 ≈ O(N 已发布 × M 缴费)，批量确认 200 份即放大 200 倍，且全部阻塞在单 writer 上；更糟的是 `rate_impact` 还会对**每一宗地**再触发一次同样的扫描。
- 它把"读膨胀"变成"写锁膨胀"：SQLite 单 writer 下，一次慢确认会级联拖垮导入、识别回写、查询等**所有**并发请求（busy_timeout=15s 后报错），即从"慢"演变为"全系统不可用"。
- 它与 P2-1（缺索引）、P2-2（全量加载）、P2-3（单线程）同源共振：单实例 SQLite + 无索引 + 写事务内全扫描 + 串行识别，构成一个在 3000 份规模下必然失稳的组合，而不是孤立 bug。

最小止血顺序（不推翻架构）：先补三处索引 + 把 `source["payments"]` 提升为启动期一次建好的字典 + 把"票据归属校验"改为宗地级索引反查（P0-1/P2-1）；再给识别任务加重试/强制重置逃生口（P0-2）；最后把 demo 模式的角色声明从请求头移除（P0-3）。这三步不动分层与模块划分，就能把"规模放大即崩溃"和"本地即管理员"两个致命面先堵上。
